# Задачи CRM

План оставшихся работ после инициализации проекта. Задачи расположены по убыванию
приоритета: сначала обязательный backend и его корректность, затем завершение
сдаваемого API, пользовательские сценарии frontend и итоговая проверка проекта.
Опциональные улучшения находятся в самом низу. Внутри разделов порядок учитывает
зависимости; тесты добавляются вместе с функциональностью, а не после всего API.

Уже готовы: каркасы Next.js и FastAPI, FSD с `src/app/providers`, зависимости и
lock-файлы, SQLAlchemy-сессии, конфигурация Alembic, `/health`, `/ready`, два
инфраструктурных теста, Dockerfile и `docker-compose.yml`. Эти работы не повторяем.
Бизнес-модели, бизнес-миграции и обязательные эндпоинты пока отсутствуют.

ТЗ ограничивает работу четырьмя часами и не требует интерфейса. Frontend включён
в план по требованиям проекта, но идёт после обязательного API. Если работа
выполняется в рамках этого лимита, учитывать фактическое время и честно записать
незавершённые задачи в README. Redis остаётся необязательным сервисом.

## P0 — решения, данные и критичные бизнес-правила

### 1. Закрепить предметные правила и контракты

- [ ] Определить статусы организации, начальное значение, допустимые переходы и
  влияние результатов звонка/событий встречи на статус. Согласовать семантику
  `GET /companies?status=` и зафиксировать её в README и архитектуре.
- [ ] Выбрать трактовку «двух активных встреч организации»: одна scheduled-запись
  вообще либо только запрет пересекающихся интервалов. Для первого варианта
  определить завершение встречи и освобождение организации для нового назначения.
- [ ] Определить статусы встречи, разрешённые действия PATCH и поведение при
  повторной отмене, переносе отменённой встречи и изменении менеджера.
- [ ] Зафиксировать связь звонка `meeting_set` с существующей встречей: обязательный
  `meeting_id`, та же организация, допустимый статус встречи. Описать поведение
  связи для `no_answer` и `refused`, а также двух отдельных запросов создания.
- [ ] Описать тела запросов/ответов, обязательные поля, формат ошибок и HTTP-коды:
  201 при создании, 404 для отсутствующих сущностей, 422 для невалидных данных,
  409 для бизнес-конфликтов. Выбрать единый ответ на успешный PATCH.
- [ ] Уточнить БИН (12 цифр, строка), уникальность БИН, минимальную валидацию
  названия/телефона, limit/offset и максимальный размер страницы.
- [ ] Зафиксировать UTC в API, отклонение datetime без timezone и политику для
  смещений, отличных от UTC; `date` расписания трактовать как день Asia/Almaty.
- [ ] Подготовить матрицу бизнес-проверок до реализации, включая конкурентные запросы.

Готово, когда сценарии и спорные случаи имеют однозначное поведение и не требуют
разных догадок в backend, frontend и тестах. Основа решений: [architecture.md](architecture.md).

- [ ] Создать SQLAlchemy-модели `companies`, `managers`, `calls`, `meetings`,

- [ ] Добавить timezone-aware поля встреч, `created_at`, неизменяемое

- [ ] Подготовить первую Alembic-миграцию и явные импорты моделей в `db/models.py`.
- [ ] Добавить `btree_gist` и EXCLUDE-ограничение пересечений активных встреч

- [ ] Добавить ограничение организации согласно решению из задачи 1: частичный

- [ ] Добавить CHECK на длительность 60 минут, FK и индексы для фактических запросов

- [ ] Добавить явную повторно запускаемую seed-команду менеджеров с известными ID.

- [ ] Подготовить отдельную PostgreSQL для интеграционных тестов и изоляцию данных.
  Исключить запуск очистки тестов против рабочей БД.

Готово, когда миграция разворачивает схему с ограничениями на чистой PostgreSQL,
а менеджеров можно получить воспроизводимой командой без ручного SQL.

### 3. Реализовать минимальные зависимости и назначение встречи

- [ ] Реализовать `POST /companies`: схема ввода/вывода, создание, проверки полей,
  обработка дубликата согласно выбранному правилу уникальности.
- [ ] Реализовать `POST /meetings` с проверкой существования организации и менеджера.
- [ ] Вынести правила времени в тестируемые функции: длительность 60 минут,
  пн–пт, 09:00–18:00 Asia/Almaty, полное попадание интервала в рабочий день.
- [ ] Вычислять конец встречи на backend; не доверять произвольной длительности
  из frontend. Конвертацию часового пояса выполнять через ZoneInfo, не фиксированный offset.
- [ ] Реализовать service/repository и одну транзакцию назначения. Предварительно
  проверять конфликты для понятного ответа, сохраняя ограничения БД как гарантию.
- [ ] Преобразовывать нарушения известных ограничений в 409 по имени/SQLSTATE,
  откатывать транзакцию и не скрывать неизвестные ошибки как «слот занят».
- [ ] Обрабатывать предметные ошибки единообразно; неожиданные ошибки логировать,
  не раскрывая клиенту SQL, пароли и внутренние трассировки.
- [ ] Добавить тесты рабочего дня: 09:00 и 17:00 допустимы; до 09:00,
  17:30 и выходные отклоняются. Проверять значения в UTC, соответствующие Almaty.
- [ ] Добавить тесты частичного, полного и вложенного пересечения; соседние
  10:00–11:00 и 11:00–12:00 должны приниматься.
- [ ] Проверить ограничение организации, включая попытку назначения другому менеджеру.
- [ ] На реальной PostgreSQL проверить два одновременных назначения с отдельными
  сессиями: конфликт у менеджера и конфликт организации; ровно одна запись
  сохраняется, проигравший запрос возвращает 409, а не 500.

Готово, когда критичные правила соблюдаются и при обычных, и при конкурентных запросах.

## P1 — остальные обязательные API, тесты и материалы сдачи

### 4. Перенос, отмена и расписание

- [ ] Реализовать `PATCH /meetings/{id}`: перенос и отмену с проверкой переходов.
- [ ] При переносе повторно проверять рабочие часы и ограничения, исключая саму
  встречу из предварительного поиска конфликтов; прежний интервал освобождать.
- [ ] Изменение встречи и запись истории сохранять одной транзакцией. Не менять
  `created_at` и `original_starts_at`; историю сделать доступной в согласованном ответе API.
- [ ] Защитить обновление одной встречи от потери изменений при конкурентных PATCH:
  выбрать блокировку строки или проверку версии; проверить сценарий тестом.
- [ ] Проверить, что отменённая встреча освобождает слот и ограничения организации.
- [ ] Реализовать `GET /managers/{id}/schedule?date=`: валидацию даты, 404 для
  неизвестного менеджера, локальные границы дня → UTC, сортировку по началу встречи.
- [ ] Добавить тесты успешного и конфликтующего переноса, отсутствия частичных
  изменений при отказе, истории нескольких переносов, отмены и повторного бронирования.
- [ ] Добавить тесты пустого расписания, фильтрации по менеджеру/дате и UTC-сериализации.

### 5. Звонки и список организаций

- [ ] Реализовать `POST /calls` с результатами `no_answer`, `refused`, `meeting_set`.
- [ ] Проверять существование организации и корректность `meeting_id`: отсутствие,
  неизвестная встреча, другая организация и недопустимый статус дают ожидаемые ошибки.
- [ ] Применять согласованные переходы статуса организации в той же транзакции,
  что и запись звонка, если переходы предусмотрены контрактом.
- [ ] Реализовать `GET /companies?status=&limit=&offset=`: фильтр, стабильную
  сортировку, пагинацию, ограничения параметров и согласованный формат метаданных.
- [ ] Добавить тесты трёх результатов звонка, ошибки `meeting_set` без встречи,
  неверных связей, фильтра, границ пагинации и пустого результата.
- [ ] Проверить минимум пять содержательных бизнес-автотестов из ТЗ; обязательные
  проверки пересечений и границы рабочего дня должны входить в этот набор.
  Инфраструктурные тесты `/health` и `/ready` их не заменяют.
