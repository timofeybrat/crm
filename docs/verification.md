# Проверка CRM

## Авторизация и TLS

- **110 backend-тестов passed** на PostgreSQL: Argon2id, сессии, CSRF/origin,
  права менеджеров, истечение/отзыв, общие конкурентные лимиты входа и видеосвязь.
- **11 E2E passed**: прежние 7 сценариев CRM и 4 сценария входа, HttpOnly,
  перезагрузки, выхода из нескольких вкладок, отказа CSRF и ограниченного менеджера.
- **2 video E2E passed по WS и 2 по WSS**: настоящий LiveKit, два браузерных
  контекста, аудиобайты и декодированные видеокадры, вход с сессией и отзыв доступа.
- Production target Next.js собран и запущен с Caddy; HTTPS/WSS override закрывает
  прямые HTTP-порты frontend/API. Секреты bootstrap-аккаунта остаются в `.env`.
- В основном Compose проверены настоящий вход, Secure HttpOnly, отказ CSRF,
  выход и отзыв доступа без изменения записей CRM. На crm_test отдельно прошли
  downgrade/upgrade миграций безопасности и `alembic check`.
- Найден и исправлен редкий PostgreSQL deadlock при конкурентном назначении:
  после rollback API возвращает 409. Отдельный тест воспроизводит настоящую
  взаимоблокировку и проверяет успешный исход одной транзакции и конфликт другой.
- Frontend lint/typecheck/Prettier, 3 unit-теста и production-сборка проходят.
  Браузерные TLS-тесты игнорируют ошибки локального CA в изолированном контексте;
  приложение не отключает проверку сертификатов. Цепочка и имя localhost отдельно
  проверены клиентом с явно доверенным экспортированным CA для приложения и LiveKit.
- Публичный домен/VPS и соединение физических устройств в разных сетях не настроены.
  Требования размещения, доверия локальному CA и ICE/TURN: [security.md](security.md).

## Видеосвязь, ветка `feat/video-calls`

- Backend: **77 passed** с PostgreSQL, включая права менеджеров, приглашения,
  окно доступа, конкурентное создание, JWT, отмену/перенос и повтор очистки
  после отказа платформы. Слабые настройки отклоняются без вывода секретов.
- Ruff, frontend lint/typecheck/Prettier и production-сборка проходят;
  3 unit-теста времени и все 7 существующих Playwright-сценариев CRM сохранены.
- **2 новых Playwright-теста** проходят с настоящим LiveKit v1.13.10 и отдельной
  БД crm_test. В двух контекстах Edge проверены полученные аудиобайты и
  декодированные видеокадры через WebRTC stats, а не только отображение элементов.
- Проверены микрофон/камера, выход и повторный вход, завершение менеджером,
  запрет нового входа по отозванной ссылке и ошибочные приглашения.
  Временный ответ 503 от CRM API сохраняет уже установленную медиасвязь.
- Просмотрены скриншоты desktop 1440px и mobile 390px; горизонтального
  переполнения нет. Все изображения используют синтетические устройства.
- Compose с профилем video собирается и запускается; backend применяет новую
  миграцию до старта. Тестовый LiveKit использует отдельные порты и фиктивные
  ключи; реальные ключи созданы только в игнорируемых файлах окружения.
- На crm_test проверены downgrade/upgrade новой миграции и `alembic check`:
  схема соответствует ORM. Конфигурация из `.env.example` оставляет видео
  выключенным и корректно передаёт пустую карту ключей менеджеров.
- В работающем Compose отдельно проверены прокси API, требование авторизации
  видео, экран гостя и страница организаций без изменения записей CRM.
- `npm run build` также выполнен в отдельном контейнере на Node.js 22.23.5:
  минимальная версия 22.22+ учитывает транзитивную зависимость LiveKit `machina`.
- Не проверены физические устройства в разных сетях, качество звука/эхо,
  внешняя конфигурация HTTPS/WSS/TURN и LiveKit Cloud. Это остаётся ручной
  проверкой перед внешним размещением; localhost-конфигурация её не заменяет.

Команды и границы доступа: [video-calls.md](video-calls.md).

- Frontend: TypeScript, ESLint с FSD-правилами, Prettier и production-сборка проходят.
- **3 unit-теста** проверяют перевод времени Almaty/UTC, историческую смену offset,
  локальную дату и навигацию по дням.
- **7 Playwright-тестов** проходят в отдельном Next.js и FastAPI, с БД crm_test.
- Проверены поиск, фильтры и пагинация, быстрый ввод и перезагрузка, создание
  организации и дубликат БИН, звонок, назначение, перенос, история, отмена,
  завершение, конфликт 409 и повтор только звонка после сбоя 503.
- Проверен сценарий назначения по свободному часу и обновления старого дня при переносе.
- Desktop 1440×1000 и mobile 390×844 проверены по скриншотам; горизонтального
  переполнения страницы нет, на телефоне используются карточки организаций.
- Проверен возврат фокуса после Escape. Скриншоты и трассы находятся только в
  игнорируемом frontend/test-results; личные данные и реальные записи не использовались.
- Основной Docker frontend пересобран и запущен на localhost:3000. Отдельный
  браузер проверил загрузку организаций и расписания через реальный API, отсутствие
  runtime-ошибок и мобильного переполнения без создания записей в рабочей БД.

## Результаты

- `uv sync --frozen`: установка в новое окружение выполнена.
- `pytest -q`: **58 passed**, включая интеграционные проверки на PostgreSQL 17;
  пропущенных тестов нет.
- `ruff check .` и `ruff format --check .`: успешно.
- `alembic upgrade head --sql`: SQL с таблицами, EXCLUDE и частичным UNIQUE сформирован.
- Upgrade → downgrade → upgrade и `alembic check` ранее выполнены на отдельной
  `crm_test`; расхождений с ORM-моделями не обнаружено.
- `docker compose up --build -d --wait`: чистый снимок собран и запущен отдельным
  проектом с новой пустой PostgreSQL. Миграции применились автоматически.
- Seed менеджеров выполнен явно, повторный запуск проверен отдельно.
- **21 запрос** из `docs/requests.http` выполнен в порядке файла: все ожидаемые
  коды 200/201/404/409/422 совпали с фактическими, ссылки на ID получены из ответов.
- Frontend и same-origin прокси `/api/ready` ответили 200 в чистом Compose-проекте.
- После проверки обнаружено и исправлено копирование вложенного host-bytecode в
  Docker-контекст. Коммит `ea6dea9` добавляет рекурсивные исключения; исправленный
  основной образ пересобран и запущен, в /app/src и /app/alembic файлов .pyc нет.
- `npm run lint`, `npm run typecheck`, `npm run build` успешно выполнены в основном
  frontend; исходники frontend не менялись в ходе реализации API.

Для проверки чистого снимка использованы отдельные порты и том PostgreSQL,
чтобы существующие контейнеры, таблицы и окружение не могли скрыть ошибку запуска.
Порт основной PostgreSQL на этой машине был занят другим сервисом, поэтому в
локальном неотслеживаемом .env проекта выбран альтернативный порт.
