# Архитектура CRM

## Объём первого этапа

Конкретные решения по статусам, активным встречам и HTTP-контрактам закреплены
в [api-contract.md](api-contract.md). При расхождении с предложениями ниже
приоритет имеет этот контракт; разделы с рекомендациями описывают исходные варианты.

Модульный монолит: один Next.js frontend, один FastAPI backend, одна PostgreSQL.
Вначале реализуем обязательные API и бизнес-правила, затем интерфейс.
Инициализация не считается готовым решением тестового задания.
В PDF frontend и Redis не требуются; добавлены по выбранному стеку проекта.
Redis запускается опционально и пока не участвует в бизнес-процессах.

## Backend

### Расширение видеосвязи после сдачи ТЗ

В ветке `feat/video-calls` выбрана LiveKit: официальные React Components для Next.js
и `livekit-api` для FastAPI. Готовый медиасервер отвечает за WebRTC; backend CRM
проверяет доступ и управляет комнатами. Это позволяет сохранить свой интерфейс по
FSD и выбирать между локальным сервером и LiveKit Cloud. Рассматривались также
Daily (внешняя платформа с React SDK/REST API) и Jitsi (встраивание готового UI).

Для первого этапа предусмотрены два участника: назначенный менеджер и гость.
Менеджер использует отдельный сильный ключ из `CRM_VIDEO_MANAGER_KEYS`; это
минимальная идентификация для видеосвязи, а не полноценная авторизация всей CRM.
Гость получает случайное приглашение, в БД сохраняется только SHA-256-хеш.
Ссылка содержит секрет во fragment, гостевые запросы передают его в теле POST.
Ключи, приглашения и токены не сохраняются в Query cache или localStorage.

Комната связана с одной встречей; подключение разрешено от 15 минут до начала
до 15 минут после окончания при статусе `scheduled`. Создать комнату и приглашение
можно заранее. Новое приглашение заменяет прежнее для последующих входов.
Идентификаторы участников стабильны для роли, вместимость комнаты — два человека;
повторное подключение той же роли может заменить прежнее соединение.
Токен выдаётся на 60 секунд только для своей комнаты, камеры и микрофона,
без прав администратора, чата и демонстрации экрана.

Завершение созвона закрывает комнату до переноса встречи и не меняет статус встречи.
Отмена/завершение встречи отзывает приглашение в одной транзакции с изменением CRM.
Перенос отзывает прежнее приглашение и требует создания новой комнаты с новым именем.
Внешнее удаление комнаты записывается в `video_cleanup` и повторяется фоновым
обработчиком каждые 10 секунд; окончание окна доступа также закрывает комнату.
Сбой медиасервера не откатывает отмену встречи и не теряет задачу очистки.
При повторе подключения используется прежнее имя комнаты, чтобы таймаут создания
у провайдера не породил дубликат. Сетевые вызовы ограничены таймаутом 5 секунд.

Для self-hosted LiveKit необходимо отключить `room.auto_create`: участник не должен
воссоздать удалённую комнату старым JWT. Истечение JWT само по себе не отключает
участника, а LiveKit обновляет токены подключённых клиентов. Поэтому отключение
участников выполняется удалением комнаты, с задержкой обработки очереди и возможной
задержкой при недоступности платформы. Запуск в интернете требует HTTPS/WSS,
настройки ICE/TURN и защиты основного публичного API CRM.

Источники: [React Components](https://docs.livekit.io/reference/components/react/installation/),
[Python SDK](https://github.com/livekit/python-sdks/tree/main/livekit-api),
[конфигурация сервера](https://github.com/livekit/livekit/blob/master/config-sample.yaml),
[жизненный цикл токенов](https://docs.livekit.io/frontends/reference/tokens-grants/).

Код группируем по предметным областям, а не по глобальным папкам всех роутеров,
сервисов и репозиториев. Точки входа и общая инфраструктура остаются отдельно:

```text
backend/
  src/crm/
    main.py                 # app factory, middleware, lifespan
    api/router.py           # сборка маршрутов
    core/config.py          # настройки CRM_* из окружения
    db/                     # Base, фабрика сессий, регистрация ORM-моделей
    modules/
      companies/
      calls/
      managers/
      meetings/
      health/
  alembic/
  tests/
```

При реализации каждый бизнес-модуль получает только необходимые файлы:

- `router.py`: HTTP, зависимости, коды ответов; не содержит бизнес-правил.
- `schemas.py`: отдельные Pydantic-модели запросов и ответов.
- `service.py`: сценарии, проверки правил, координация и границы транзакций.
- `repository.py`: конкретные запросы SQLAlchemy; не вызывает commit.
- `models.py`: ORM-модели и декларативные ограничения.
- `exceptions.py`: предметные ошибки, когда они появятся.

Это прагматическое разделение ответственности, а не полная реализация Clean
Architecture. Пока сервисам допустимо работать с конкретными репозиториями и
SQLAlchemy-сессией. Не создаём отдельные копии ORM-сущностей, интерфейсы для каждого
класса, GenericRepository, CQRS, event bus или собственный DI-контейнер.
Паттерны: Service Layer, конкретные Repository, Dependency Injection через FastAPI.
Транзакция SQLAlchemy выполняет роль Unit of Work; отдельная обёртка пока не нужна.
Чистые правила времени можно вынести в функции без зависимостей от FastAPI и БД.

Одна AsyncSession на запрос; сессию нельзя разделять между параллельными задачами.
Сервис открывает транзакцию до первого чтения сценария (`async with session.begin()`).
Завершение сценария атомарно: изменение встречи и запись истории сохраняются вместе.
Сессия закрывается через yield-зависимость. Не выполняем commit внутри репозиториев.
Межмодульные сценарии вызывают явные функции сервисов, без HTTP-вызовов внутри приложения.
Если сценарий связывает звонок и встречу, он должен иметь одного владельца транзакции:
внутренние функции не открывают вложенный независимый commit.

## Данные и конкурентные назначения — план реализации

Реализованные таблицы: `companies`, `managers`, `calls`, `meetings`, `meeting_history`.
Поля БИН и телефон — строки. Проверка БИН: 12 цифр; дополнительные правила и
уникальность БИН должны быть явно оговорены, поскольку ТЗ их не задаёт.
Для дат встреч — timezone-aware значения и PostgreSQL TIMESTAMPTZ.
Хранение и API — UTC; рабочие часы — через ZoneInfo("Asia/Almaty"), без фиксированного offset.
Расписание на день: локальные границы дня переводятся в UTC перед запросом к БД.

Встреча имеет `starts_at`, `ends_at`, `status`, неизменяемые `created_at` и
`original_starts_at`. История сохраняет прежний и новый интервал, тип изменения и
время изменения. `created_at` — когда запись создана, `original_starts_at` — на какое
время встречу назначили первоначально: это разные сведения.

Для пересечений менеджера рекомендовано ограничение PostgreSQL EXCLUDE USING GIST:
равенство `manager_id` и пересечение `tstzrange(starts_at, ends_at, '[)')` для
активных записей. Потребуется расширение `btree_gist` в миграции.
Полуоткрытые интервалы разрешают соседние встречи 10:00–11:00 и 11:00–12:00.
Сначала сервис даёт понятную диагностику, затем ограничение БД защищает от гонки.
При нарушении известного ограничения транзакция откатывается, API возвращает 409.
Нельзя превращать любой IntegrityError в «слот занят»: проверяем конкретное имя
ограничения/SQLSTATE. Неизвестные ошибки логируются и остаются серверными ошибками.
Redis-lock не используется как гарантия целостности расписания.

Правило организации неоднозначно. Рекомендация для первой реализации: не более
одной встречи в статусе scheduled у организации вообще; закрепить частичным
уникальным индексом по company_id. Тогда нужно явно определить завершение встречи:
например, добавить статус completed и переход через PATCH. Если требуется только
запрет временных пересечений, вместо уникального индекса нужен EXCLUDE по company_id.
Окончательное толкование должно быть закреплено перед первой бизнес-миграцией;
автоматически не считать встречу завершённой только потому, что время прошло.

## Контракты API — предлагаемые решения

- Существующие сущности ищем по ID; отсутствующие возвращают 404.
- Ошибки входных данных и рабочих часов — 422, конфликт записи — 409.
- Для POST /calls с meeting_set использовать существующий meeting_id и проверить,
  что встреча относится к той же организации; для других результатов связь не нужна.
- Сначала создать встречу через POST /meetings, затем связать звонок. Это два
  независимых запроса; атомарность обоих не обещается. Если она понадобится,
  вводится отдельный объединённый сценарий с одной транзакцией.
- date расписания — локальная календарная дата Asia/Almaty.
- Принимать UTC с Z или +00:00; naive datetime и другие смещения отклонять,
  если следовать формулировке ТЗ строго. Ответы сериализовать в UTC.
- Статус организации и его переходы надо определить до реализации фильтра;
  не смешивать автоматически последний результат звонка со статусом встречи.
- Начальная пагинация: limit/offset с верхним пределом и стабильной сортировкой по ID.
- Менеджеров для демонстрации создавать отдельной явной seed-командой после миграций.
  Таблицы и тестовые данные не создаются побочным эффектом импорта приложения.

Это рекомендации, а не уже реализованные API-контракты.

## Frontend: FSD

```text
frontend/
  app/                     # тонкие Next.js route entry points
  pages/README.md          # не даёт Next.js принять src/pages за Pages Router
  src/
    app/providers/         # провайдеры приложения
    app/styles/
    pages/companies/       # композиция страницы организаций
    pages/schedule/        # композиция страницы расписания
    widgets/               # таблица организаций, календарь менеджера
    features/              # действия: создать, записать звонок, назначить, перенести
    entities/              # company, call, meeting, manager
    shared/api/            # транспорт HTTP
```

Импорты идут сверху вниз: app → pages → widgets → features → entities → shared.
Слайсы одного слоя не импортируют внутренности соседних слайсов. Внешние импорты
слайса — через публичный index.ts. Композиция нескольких сущностей — в feature
или выше. Не создаём пустую иерархию ui/model/api/lib для каждого будущего слайса.
ESLint запрещает alias-импорты верхних слоёв, соседних слайсов и обход публичных API.
Внутри слайса используются относительные импорты; публичные index.ts содержат реэкспорты.

TanStack Query хранит серверные данные и управляет invalidation после мутаций.
Zustand — только клиентское состояние, которое действительно нужно нескольким
компонентам: например, открытая панель. Не дублируем Query cache в Zustand.
Для простого локального состояния достаточно useState; фильтры и выбранную дату,
которыми нужно делиться ссылкой, лучше хранить в URL.
Формы — react-hook-form, правила — Zod и zodResolver.
Общую библиотеку компонентов выделяем по мере повторения интерфейса.

AppProviders — client boundary в src/app/providers. QueryClient создаётся на
экземпляр провайдера, не как глобальный singleton на сервере.
Текущая документация FSD рекомендует префиксы _app/_pages для Next.js. В этом
проекте сохраняем app/providers по требованию проекта; корневые app и pages
резервируют Next.js-роутинг, чтобы src содержал FSD-слои. Сборка проверяет эту схему.
Провайдеры QueryClient, уведомлений и UI-store находятся в src/app/providers.
Zustand хранит только ID открытой карточки, отдельный экземпляр store создаётся
на экземпляр провайдера. Серверные данные не копируются в store.
Реализованы формы организации, звонка и встречи с react-hook-form и Zod.
HTTP-клиент пока отвечает за транспорт; тип T не валидирует ответ во время
исполнения. API каждой сущности валидирует ответ Zod-схемой перед передачей в кеш.
Браузер обращается к /api, Next.js проксирует на API_INTERNAL_URL.
В серверных компонентах нужен отдельный абсолютный URL и осознанная cache policy.
API_INTERNAL_URL задаётся до next dev/build; для standalone production нельзя
предполагать, что смена переменной после сборки изменит rewrites.

## Последовательность разработки

1. Уточнить статусы и неоднозначности. ORM-модели и первая миграция с ограничениями.
2. Организации: создание, список, фильтры и пагинация; seed менеджеров.
3. Встречи: временные правила, транзакции, PostgreSQL constraints и конфликты.
4. Перенос, отмена, история и дневное расписание.
5. Звонки с проверкой связи meeting_set.
6. Интеграционные тесты на реальной PostgreSQL, включая два конкурентных запроса.
7. Frontend-сценарии поверх проверенных контрактов, примеры запросов и REFLECTION.md.

Обязательные проверки: соседние и пересекающиеся интервалы; начало в 09:00,
17:00 и 17:30; выходной; повторная активная встреча организации; отмена и повторное
бронирование; перенос без потери истории; meeting_set без корректной встречи;
два конкурентных назначения. SQLite не заменяет PostgreSQL в этих тестах.
