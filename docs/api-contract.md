# Контракт CRM API (MVP)

В ветке `feat/video-calls` поверх бизнес-контрактов ниже добавлена обязательная
авторизация: все CRM endpoints требуют сессию, изменяющие запросы — также CSRF
и разрешённый Origin. Менеджер изменяет свои встречи, администратор — встречи
команды. Гостевой доступ к видео основан на приглашении. Полный контракт входа,
выхода и ограничения частоты запросов: [security.md](security.md).

Это принятые решения по неоднозначностям ТЗ. Backend и тесты должны следовать
этому контракту; изменения контракта фиксируются до изменения поведения.

## Общие правила

- ID: положительные целые числа. Название организации и имя менеджера: 1–200
  символов после удаления пробелов по краям. БИН: строка из 12 ASCII-цифр,
  уникальная для организации. Телефон: строка 5–32 символа, без попытки угадать страну.
- Все datetime в запросах — ISO 8601 с Z или нулевым UTC offset. Даты без
  timezone и другие offset отклоняются. Ответы — UTC. Рабочее время проверяется
  через ZoneInfo("Asia/Almaty"). date расписания — локальный день этого пояса.
- Создание — 201, чтение и PATCH — 200; нет сущности — 404; конфликт — 409;
  невалидный ввод/рабочее время/недопустимое действие — 422.
- Ошибки имеют стандартное поле detail FastAPI: строка для предметной ошибки
  либо список ошибок валидации. Внутренние исключения не отправляются клиенту.
- Пагинация: limit=20 (1–100), offset=0 (>=0), ответ {items, total, limit, offset}.
  Сортировка организаций по id по возрастанию.

## Статусы организации

new, no_answer, refused, meeting_set. Новая организация имеет статус new.
Статус отражает результат последнего зарегистрированного звонка. Любой новый
звонок заменяет предыдущий статус. Назначение/отмена/перенос встречи сами по себе
статус не меняют: это история коммуникации, а не вычисляемый статус расписания.
Поэтому meeting_set может сохраниться после отмены встречи; это осознанное решение.

## Встречи и конкурентность

- Длительность всегда 60 минут, ends_at вычисляется backend.
- Пн–пт, 09:00–18:00 Almaty. Начало 09:00 и 17:00 допустимо, 17:30 — нет.
- Статусы: scheduled, cancelled, completed. Активная означает scheduled.
  У организации может быть только одна scheduled-встреча вообще, независимо от
  даты и менеджера. Для следующей встречи предыдущую отменяют или завершают.
- У менеджера scheduled-встречи не пересекаются; соседние интервалы разрешены.
  Ограничения БД защищают оба правила при конкурентных запросах.
- POST создаёт scheduled-встречу. PATCH принимает ровно одно действие:
  {action: reschedule, starts_at, manager_id?}, {action: cancel}, {action: complete}.
  У завершённой/отменённой встречи перенос и другие переходы запрещены (422).
  Повторный cancel для cancelled и complete для completed идемпотентны (200).
- Завершать встречу можно только после ends_at. Встречи в прошлом не запрещены
  ТЗ; POST и reschedule допускают их при соблюдении остальных правил.
- PATCH блокирует строку встречи на время транзакции. Последовательные переносы
  допустимы и оба сохраняются в истории. Перенос после конкурентной отмены — 422.
- История содержит создание, перенос, отмену и завершение: время события,
  прежний/новый интервал, менеджера и статус. Возвращается в ответе встречи.
  created_at и original_starts_at никогда не меняются при переносах.
- Изменение встречи и истории атомарно; конфликт не оставляет частичных записей.

## Эндпоинты

| Метод | Путь | Ввод и результат |
|---|---|---|
| POST | /companies | {name, bin, phone} → организация |
| GET | /companies | status?, limit?, offset? → страница организаций |
| GET | /companies/{id} | организация, active_meeting, последние 10 встреч и 10 звонков |
| POST | /meetings | {company_id, manager_id, starts_at} → встреча с историей |
| PATCH | /meetings/{id} | action и поля действия → встреча с историей |
| GET | /meetings/{id} | встреча с историей для повторного просмотра; расширение ТЗ |
| POST | /calls | {company_id, result, meeting_id?} → звонок |
| GET | /managers/{id}/schedule | date=YYYY-MM-DD → {manager_id, date, meetings} |
| GET | /managers | список менеджеров для frontend; небольшое расширение ТЗ |

В расписание входят scheduled-встречи, начало которых попадает в локальный день;
сортировка по starts_at, затем id. Неизвестный менеджер — 404, пустой день — 200.
Каждая запись расписания дополнительно содержит company_name для отображения.
Список организаций поддерживает search (до 200 символов): поиск без учёта регистра
по названию, БИН и телефону, вместе с фильтром статуса и пагинацией.
Символы % и _ ищутся буквально. Данные карточки возвращаются через GET /companies/{id}:
recent_calls и recent_meetings отсортированы по ID по убыванию, active_meeting —
единственная scheduled-встреча либо null. Это расширения для frontend-сценариев.

Для meeting_set обязательна существующая scheduled-встреча той же организации.
У no_answer/refused meeting_id должен отсутствовать или быть null.
Сначала POST /meetings, затем POST /calls — две независимые транзакции; ошибка
второго запроса не удаляет созданную встречу. Клиент должен показывать этот случай.
Звонок и обновление статуса организации сохраняются одной транзакцией.
Менеджеры создаются явной идемпотентной seed-командой; CRUD менеджеров не нужен.

## Матрица проверок

| Область | Сценарии |
|---|---|
| Организации | валидное создание, дубликат БИН, пустое имя, БИН не 12 цифр, фильтр, страницы |
| Время | 09:00/17:00 разрешены, до 09:00/17:30/выходной запрещены, naive/non-UTC запрещены |
| Пересечения | полное, частичное, вложенное; соседние разрешены; другой менеджер разрешён |
| Организация | вторая scheduled запрещена даже в другую дату с другим менеджером |
| Конкурентность | две отдельные сессии: ровно один POST успешен, второй 409 |
| PATCH | история нескольких переносов, неизменяемое исходное время, rollback конфликта |
| Отмена/завершение | слот освобождается, повторное действие идемпотентно, перенос терминальной запрещён |
| Расписание | локальные границы дня, менеджер, сортировка, пустой результат, 404 |
| Звонки | все исходы, отсутствие/чужая/отменённая встреча, обновление статуса атомарно |

PostgreSQL-интеграционные тесты используют отдельную БД; SQLite не проверяет EXCLUDE.
