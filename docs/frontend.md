# Frontend CRM «Пульс»

## Экран организаций

Поиск выполняется на backend по всей базе, включая название, БИН и телефон.
Статус, поисковая строка и страница хранятся в URL. Ввод не теряется при быстрых
изменениях: поле хранит нативный черновик, запросы используют debounce 300 мс.
На компьютере отображается таблица, на узком экране — карточки без горизонтального скролла.
Статистика получает реальные total для соответствующих фильтров, не вымышленные проценты.

Карточка организации открывается сбоку. В ней доступны контакты, последний результат
звонка, активная встреча, последние 10 звонков и 10 встреч. История встречи читается
отдельным запросом и содержит первоначальное время и все изменения.

## Встречи и звонки

Назначение доступно из карточки и из расписания. На форме можно найти организацию,
выбрать менеджера, дату и время Алматы. Занятые интервалы недоступны для выбора;
при сохранении окончательное решение принимает backend. Рабочий слот — 60 минут.
Предусмотрены перенос, отмена с подтверждением и завершение после времени окончания.

Новая встреча по умолчанию сопровождается записью звонка meeting_set; флажок
можно отключить. Это две операции API. Если вторая не удалась, форма показывает,
что встреча уже создана, и предлагает повторить только звонок.
Автоматические повторы мутаций отключены; данные формы сохраняются при конфликте 409.
Все запросы имеют timeout 15 секунд, чтобы форма не оставалась заблокированной бесконечно.

После мутаций обновляются организации, карточки, детали встреч и расписания.
Перенос обновляет кеш как старого, так и нового дня/менеджера.
Даты переводятся через IANA Asia/Almaty, без фиксированного UTC offset и без
зависимости от часового пояса компьютера.

## Структура FSD

```text
frontend/app/                       # тонкие entry points Next.js
frontend/src/
  app/providers/                    # QueryClient, CompanyPanel, Toast
  app/styles/                       # визуальная система приложения
  pages/companies/                  # URL-состояние и композиция страницы
  pages/schedule/
  widgets/company-table/
  widgets/company-overview/
  widgets/company-workspace/        # композиция карточки из features/entities
  widgets/schedule/
  widgets/workspace-shell/
  features/create-company/
  features/record-call/
  features/manage-meeting/
  entities/company/                 # model, api, ui; серверные данные не в Zustand
  entities/call/
  entities/meeting/
  entities/manager/
  shared/api/                       # HTTP, отмена запроса, timeout
  shared/lib/                       # время, ошибки, небольшие hooks
  shared/ui/                        # Button, Field, Modal, feedback
```

Провайдеры размещены в app/providers. Контексты/фабрики состояния определены ниже
по слоям, чтобы entities и shared не импортировали app. Zustand хранит только ID
открытой карточки; экземпляр создаётся на экземпляр провайдера, не глобально на сервере.
Данные API валидируются Zod перед записью в TanStack Query. Формы используют
react-hook-form + zodResolver. UI-состояние формы не дублируется в Query cache.

Публичный API слайса — index.ts с реэкспортами. ESLint проверяет alias-импорты:
верхние слои, соседние слайсы и обход публичного API запрещены. Внутренние
относительные импорты остаются внутри слайса. Прямые относительные переходы
между слайсами не допускаются соглашением; текущий lint контролирует только alias-импорты,
а произвольные относительные переходы требуют проверки на ревью.

## Доступность и проверка

Модальные окна используют Radix Dialog: удержание фокуса, Escape, возврат к
вызвавшему элементу и последовательность вложенных окон. Формы имеют labels,
сообщения валидации, pending-состояния и защиту от повторного отправления.
Есть skip-link, live-уведомления, видимый клавиатурный фокус и reduced-motion.

Команды из frontend:

```sh
npm run lint
npm run typecheck
npm run format:check
npm test
npm run build
npm run test:e2e
```

Для разработки используется Node.js 22.22+ с учётом зависимостей LiveKit;
`npm test` использует встроенную поддержку TypeScript stripping.

E2E требует PostgreSQL crm_test и backend/.env.test, как описано в README.
Тестовый сервер очищает только crm_test; не запускать одновременно с pytest.
Браузерные сценарии CRM идут через реальные API, кроме явно смоделированных ошибок
503 записи звонка и 409 конкурентного назначения. Демо-записи создаются только
в тестовой БД; в основную crm они не добавляются.

## Видеовстречи

Маршруты `/video/meetings/[meetingId]` и `/video/guest` собирают страницу
`pages/video-call`. `entities/video-call` содержит Zod-контракты и HTTP API,
`features/manage-video-call` — создание, приглашение и закрытие комнаты,
`widgets/video-room` — проверку устройств и интерфейс медиасвязи.
`VideoRoomProvider` находится в `app/providers` и передаётся странице из маршрута:
нижние слои не импортируют `app`. Браузерный SDK загружается для видеостраниц
через client boundary с отключённым SSR.

Приглашения и JWT живут только в состоянии вкладки, без Query cache
и localStorage. Состояние защищённой комнаты обновляется отдельным опросом API;
временный сбой не прерывает установленный звонок, окончательный отказ в доступе
размонтирует комнату. Новые запросы опроса не накладываются друг на друга,
при уходе со страницы ожидающий запрос отменяется.
Порядок запуска и E2E-проверки: [video-calls.md](video-calls.md).

## Вход и сессия

`entities/session` содержит контекст, DTO пользователя и API входа/выхода;
`features/sign-in` и `features/sign-out` — действия, `pages/login` — экран.
SessionProvider и SessionBoundary находятся в `app/providers`. Приватные страницы
ждут проверки `/auth/me`; гостевой видеоэкран доступен без входа.
Query хранит только сведения о пользователе, сама сессия — HttpOnly cookie.
Общий HTTP-клиент передаёт CSRF в изменяющих запросах, 401 закрывает приватный UI.
При выходе и смене аккаунта кеш очищается, вкладки получают сигнал BroadcastChannel.
Детали прав и HTTPS: [security.md](security.md).
