# CRM

CRM «Пульс» для организаций, звонков и встреч. Стек: Next.js, TypeScript,
TanStack Query, Zustand, Zod, react-hook-form, Tailwind CSS; FastAPI, SQLAlchemy,
Alembic, Pydantic, PostgreSQL; Docker Compose. Redis доступен отдельным профилем.

## Текущее состояние

Инициализированы приложения, FSD-структура, конфигурация миграций, зависимости
с lock-файлами, Dockerfile и Compose. Backend предоставляет GET /health и GET /ready.
Frontend предоставляет рабочие экраны организаций и расписания. ORM-модели и миграция готовы:
PostgreSQL защищает длительность, пересечения менеджера и активную встречу организации.
Есть идемпотентный seed менеджеров и интеграционные тесты ограничений на отдельной БД.
Все обязательные API реализованы: организации, звонки, назначение, перенос,
отмена и расписание. Есть чтение встречи с историей и список менеджеров.
Проверяются рабочие часы, конкурентные конфликты и атомарность изменений.
Интерфейс адаптирован для компьютера и телефона: поиск по всей базе, фильтры,
пагинация, карточка организации, запись звонков, назначение/перенос/отмена/завершение
встреч и история. Счётчики используют реальные данные API; демо-данные не подмешиваются.
Принятые компромиссы и конкурентность описаны в [REFLECTION.md](REFLECTION.md).

В ветке `feat/video-calls` добавлены видеосвязь, вход менеджеров, серверные сессии,
CSRF, роли и HTTPS/WSS. Все операции CRM требуют входа; гость видеовстречи
использует приглашение. Настройка аккаунтов и TLS: [docs/security.md](docs/security.md).

Рекомендации и спорные требования: [docs/architecture.md](docs/architecture.md).
Принятые правила MVP: [docs/api-contract.md](docs/api-contract.md).
План оставшихся работ по приоритету: [docs/tasks.md](docs/tasks.md).

## Запуск Docker Compose

Нужны Docker Engine / Docker Desktop с Linux containers и Docker Compose v2.
Конфигурация находится в `docker-compose.yml` в корне репозитория.
Все команды этого раздела выполняются из корня склонированного репозитория.
Node.js, Python и uv на компьютере для этого способа запуска не нужны.

Файл `.env` необязателен: Compose использует значения по умолчанию из конфигурации.
Если нужно изменить порты или реквизиты PostgreSQL, **перед запуском** создайте его
из примера и отредактируйте. Существующий `.env` не перезаписывайте:

```sh
cp .env.example .env
```

Запуск в фоне с пересборкой образов и ожиданием готовности сервисов:

```sh
docker compose up -d --build --wait
```

Первый запуск скачивает образы и устанавливает зависимости, поэтому может занять
несколько минут. Команда возвращает управление терминалу; логи можно открыть отдельно:

```sh
docker compose logs -f frontend backend
```

При стандартных портах:

- Приложение: http://localhost:3000
- Swagger: http://localhost:8000/docs
- Liveness: http://localhost:8000/health
- Readiness (соединение с PostgreSQL): http://localhost:8000/ready

Compose запускает `alembic upgrade head` перед API при старте backend-контейнера.
При ошибке миграции Uvicorn не запускается. Для демонстрационных менеджеров после старта:

```sh
docker compose exec backend /app/.venv/bin/python -m crm.seed
```

Команда идемпотентна; ID менеджеров 1 и 2, данные демонстрационные. Seed не запускается
автоматически; без него на новой БД список менеджеров будет пуст.
Для первого входа создайте аккаунт администратора (пароль вводится скрыто):

```sh
docker compose exec backend /app/.venv/bin/python -m crm.modules.auth.provision --manager-id 1 --login manager1 --role admin
```

Затем откройте `/login`. Общего пароля по умолчанию нет. Повторный запуск команды
сбрасывает пароль и отзывает сессии; не используйте её как обычный startup-шаг.

Frontend в Compose запускается в development-режиме; после изменения файлов
повторите `docker compose up -d --build --wait`. Bind mounts пока не настроены,
поэтому изменения файлов на компьютере не подхватываются контейнерами автоматически.
HTTPS override использует проверенный production target frontend. Для запуска:

```sh
docker compose -f docker-compose.yml -f docker-compose.https.yml --profile video up -d --build --wait
```

Адрес — `https://localhost:8443`, прямые порты 3000/8000 в этом режиме закрыты.
Для ручного браузерного теста доверьте локальный CA по [инструкции](docs/security.md#httpswss).

При изменении BACKEND_PORT/FRONTEND_PORT адреса выше меняются соответственно.
Настройки backend и прокси frontend в Compose передаются напрямую;
локальные `backend/.env` и `frontend/.env.local` этому способу запуска не нужны.
Локальные пароли из примеров не использовать для публичного развёртывания.
POSTGRES_DB/POSTGRES_USER/POSTGRES_PASSWORD инициализируют пустой том PostgreSQL.
Изменение этих значений после первого запуска не переименует существующую БД
и не сменит пароль уже созданного пользователя; существующую БД нужно настраивать
отдельно либо использовать новый том.

Опционально Redis:

```sh
docker compose --profile redis up -d --build --wait
```

Redis пока не подключён к backend и не нужен для работы API.
Остановка основного стека без удаления постоянных томов: `docker compose down`.
Данные рабочей БД хранятся в именованном томе; не добавляйте `--volumes`, если
хотите их сохранить. Уже запущенный сервис отдельного профиля можно остановить
явно: `docker compose stop postgres-test` или `docker compose stop redis`.
Дополнительные замечания: [infra/README.md](infra/README.md).

## Локальная разработка

Нужны Node.js 22.22+, npm, Python 3.11+ и uv 0.11.8+.
Минимальная версия Node.js учитывает зависимости LiveKit и выполнение TypeScript
unit-тестов без отдельного runner. В Docker используется актуальный образ Node.js 22.
Команды npm в PowerShell при запрете скриптов можно выполнять как `npm.cmd`.
Команды копирования ниже подходят для Git Bash; в PowerShell можно использовать
`Copy-Item исходный-файл целевой-файл`. Уже настроенные `.env` не перезаписывайте.

При первой настройке из корня создайте настройки локального backend:

```sh
cp backend/.env.example backend/.env
```

Значения примера соответствуют стандартным настройкам Compose: PostgreSQL на
localhost:5432. Корневой `.env` читает Compose, а локальный backend — `backend/.env`;
они не синхронизируются автоматически. Если в корневом `.env` задан, например,
`POSTGRES_PORT=55432`, такой же порт должен быть в `CRM_DATABASE_URL` файла
`backend/.env`. При стандартных демонстрационных реквизитах:

```dotenv
CRM_DATABASE_URL=postgresql+asyncpg://crm:crm_local_only@localhost:55432/crm
```

При изменении имени БД, пользователя или пароля обновите URL тоже. Все настройки
backend имеют префикс CRM_. Не коммитьте реальные `.env`.

Из корня остановите контейнерные приложения, если они уже занимают порты 3000/8000,
и запустите только рабочую PostgreSQL с ожиданием готовности:

```sh
docker compose stop frontend backend
docker compose up -d --wait postgres
```

Backend — в отдельном терминале, начиная из корня проекта:

```sh
cd backend
uv sync --frozen
uv run alembic upgrade head
uv run python -m crm.seed
uv run uvicorn crm.main:app --app-dir src --reload
```

Локально миграции применяются отдельной командой выше, а не автоматически при
запуске Uvicorn. API: http://localhost:8000, Swagger: http://localhost:8000/docs.

Frontend — в ещё одном терминале, начиная из корня проекта:

```sh
cd frontend
npm ci
npm run dev
```

Интерфейс: http://localhost:3000. Оба приложения подхватывают изменения исходников:
Next.js через dev-сервер, backend через `--reload`.
По умолчанию прокси обращается к http://127.0.0.1:8000. Для изменения перед запуском
скопируйте `frontend/.env.example` в `frontend/.env.local`, настройте API_INTERNAL_URL
и перезапустите Next.js. Корневые BACKEND_PORT/FRONTEND_PORT сами по себе не меняют
порты локальных dev-серверов. Например, backend на 8001 запускается с `--port 8001`,
а frontend на 3002 — командой `npm run dev -- --port 3002`.
При изменении origin frontend добавьте его в CRM_CORS_ORIGINS локального backend.
Для `npm run build` URL прокси должен быть настроен до сборки: rewrites входят в её результат.

## Интерфейс

- `/companies`: поиск по названию, БИН и телефону, статусы последнего звонка,
  пагинация и создание организации. На телефоне вместо широкой таблицы — карточки.
- Карточка открывается сбоку: контакты, активная встреча, последние 10 звонков
  и 10 встреч. История отдельной встречи доступна из карточки и связанных звонков.
- `/schedule`: выбор дня и менеджера, рабочие часы, назначение по свободному часу.
  Фильтры, выбранный день и менеджер сохраняются в URL.
- Даты и время отображаются по Asia/Almaty, в API отправляется UTC. Выбор
  времени учитывает занятые интервалы; сервер остаётся окончательной проверкой.
- Если встреча создана, а запись звонка не удалась, показывается отдельное состояние
  с повтором только звонка. Автоматические повторы POST отключены.

Frontend следует FSD: `app → pages → widgets → features → entities → shared`.
Провайдеры находятся в `frontend/src/app/providers`; Zustand хранит только ID
открытой карточки, серверные данные — в TanStack Query. Формы используют
react-hook-form и Zod. ESLint проверяет границы слоёв и публичные alias-импорты слайсов.

## API и демонстрация

Полный контракт и допущения: [docs/api-contract.md](docs/api-contract.md).
Последовательные примеры для VS Code REST Client: [docs/requests.http](docs/requests.http).
Swagger доступен на /docs. В примерах используются только демонстрационные данные;
их удобнее выполнять на свежей базе после seed менеджеров.

Все шесть обязательных эндпоинтов реализованы. Дополнительно доступны GET /managers,
GET /meetings/{id}, GET /companies/{id} и параметр search списка организаций.
Дата расписания относится к Almaty, но timestamps принимаются и возвращаются в UTC.
У организации не более одной scheduled-встречи вообще; PATCH с action=complete
после окончания встречи либо action=cancel освобождает организацию.
Статус организации отражает последний звонок и не пересчитывается при отмене встречи.
Для meeting_set сначала создаётся встреча, затем звонок с её ID; это два независимых
запроса. Успешное создание встречи не откатывается, если запись звонка не удалась.

Время в прошлом разрешено: запрет не задан ТЗ. Праздники, обеденные перерывы,
очереди, уведомления и Redis-кэш не реализованы. Вход менеджеров, роли
admin/manager и защита API реализованы; настройки описаны в docs/security.md.
Для тестов интеграции используется одна отдельная БД crm_test; запускать этот набор
последовательно, без параллельного pytest-xdist против того же экземпляра БД.

## Проверки

Проверки на компьютере требуют инструментов из раздела локальной разработки,
даже если само приложение запускается в Docker.
Интеграционные тесты используют исключительно БД `crm_test` (не рабочую `crm`).
Из корня запустите отдельную PostgreSQL с временным хранилищем:

```sh
docker compose --profile test up -d --wait postgres-test
```

При первой настройке создайте файл тестового подключения:

```sh
cp backend/.env.test.example backend/.env.test
```

Тестовая PostgreSQL доступна на localhost:5543; внутри контейнера её порт — 5432.
Этот порт задан в Compose отдельно от POSTGRES_PORT рабочей БД.
Можно вместо файла задать CRM_TEST_DATABASE_URL через окружение.
Тесты применяют миграции и очищают
предметные таблицы **только в crm_test**. При отсутствии настройки интеграционные
тесты пропускаются с явным сообщением; для полной проверки их нельзя пропускать.
Хранилище postgres-test — tmpfs, поэтому тестовые данные не сохраняются после
остановки контейнера.

Backend-проверки — в отдельном терминале из корня:

```sh
cd backend
uv sync --frozen
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
uv run alembic upgrade head --sql
```

Frontend-проверки — в отдельном терминале из корня:

```sh
cd frontend
npm ci
npm run lint
npm run typecheck
npm run format:check
npm test
npm run build
```

Из корня: `docker compose config --quiet`.
Полный запуск контейнеров требует запущенного Docker Engine.
Результаты проверки чистого снимка: [docs/verification.md](docs/verification.md).

### Браузерные тесты

Сначала выполните шаги запуска тестовой PostgreSQL и настройки `backend/.env.test`
из раздела выше. Затем установите зависимости, начиная из корня в отдельном терминале:

```sh
uv sync --project backend --frozen
cd frontend
npm ci
```

На Windows нужен установленный Microsoft Edge. На Linux/macOS перед первым запуском,
из того же терминала в frontend:

```sh
npx playwright install chromium
```

Запуск браузерных тестов, из frontend:

```sh
npm run test:e2e
```

Playwright запускает отдельные API (18001) и Next.js (3001), затем останавливает
их. Рабочий API на 8000 и БД crm не затрагиваются. Тестовый сервер **очищает crm_test**,
применяет миграции и создаёт демо-менеджеров; имя БД проверяется перед очисткой.
Не запускать одновременно с pytest против той же тестовой БД.
Порты 18001 и 3001 должны быть свободны; уже запущенные dev-серверы на этих
портах нужно остановить.
Скриншоты и трассы пишутся в игнорируемый `frontend/test-results`; в Git и Docker
они не попадают. В скриншотах используются только тестовые демонстрационные записи.

## Аудио/видеосозвоны

В ветке `feat/video-calls` добавлена интеграция LiveKit: отдельная комната встречи,
приглашение гостя, проверка устройств и управление аудио/видео. Это расширение
сверх исходного ТЗ. Инструкция настройки ключей, локального запуска и отдельных
браузерных тестов: [docs/video-calls.md](docs/video-calls.md).

По умолчанию в примерах окружения видеосвязь выключена; основная CRM запускается
без медиасервера. Локальная конфигурация LiveKit предназначена для localhost.

## Миграции при дальнейшей разработке

После создания моделей импортировать их в src/crm/db/models.py. С запущенной БД,
из backend:

```sh
uv run alembic revision --autogenerate -m "create crm tables"
uv run alembic upgrade head
```

Проверять сгенерированный SQL вручную. PostgreSQL EXCLUDE и частичные индексы
должны быть явно проверены/добавлены в миграции; autogenerate не заменяет ревью.
